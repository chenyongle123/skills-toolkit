## 2. 三处正面冲突与取舍建议

### 冲突 1｜要不要主编排

| | A | B |
|---|---|---|
| 主张 | 不设。四个 Skill 靠 I/O 契约串联，任一平台按顺序调用即可 | 设。根 `SKILL.md` 为接入层，识别意图、编排子 Skill、汇总产出 |
| 优点 | 每个 Skill 可单独安装、单独验收；符合"4 个可独立安装"的初衷 | 状态机、三个人工关卡、断点续做有明确归属；用户只说一句话即可跑全链 |
| 缺点 | 状态机与关卡无人承接（= 我的 D3） | 多一个安装单元；弱平台可能只加载到根 SKILL.md 就停住 |

**建议：合成——保留 B 的主编排，但压到"薄路由"。**
根 `SKILL.md` 只做四件事：识别当前 stage、告诉用户下一步调哪个 Skill、校验交接产物存在、汇总产出清单。**不承载任何业务规则**（业务规则全部在子 Skill）。这样既解决 D3，又不破坏子 Skill 的独立可用性。
硬性约束：根 SKILL.md **不超过 80 行**；即使被单独安装，四个子 Skill 仍能各自跑通。

### 冲突 2｜阶段怎么切

A：阶段1 响应策划 → 阶段2 合规 → 阶段3 正文。
B：阶段1 = 响应策划 + 合规自检合并（P0）→ 阶段2 正文。

**建议采纳 B。** 理由：合规自检读的是任务卡（`03_bid-plan.json`），而任务卡正是阶段 1 的产物。若分两段，等于把同一份产物拆成两次验收，中间还要多一轮交接与返工。合并后验收标准也更清晰：**"任务卡无落点遗漏 + 偏差表无跳条 + 废标项无未响应"三件事一次过**。

### 冲突 3｜以哪个开源项目为主蓝本

| 项目 | 实测（2026-10-17 API） | 适合当什么 |
|---|---|---|
| bid-toolkit | 5 star / 1 fork，2026-08-31 建库，最后 push 2026-09-09；Python 1.8MB；license API 报 `NOASSERTION`（README 自称 CC BY-NC 4.0） | **形态参考**：skill + scripts 的组织方式、格式铁律、暗标脱敏、判词库 |
| OpenBidKit_Yibiao | **3,161** star / 810 fork，2026-10-16 仍在更新，AGPL-3.0 | 模块设计参考（全局事实设定、查重四维） |
| BidGenie_flow | **1** star / 0 fork，2026-09-15 建库当天即最后提交，**无许可证** | 只能作**思路**参考，且不可抄其提示词文案 |
| bidding_document_generator | 53 star / 6 fork，**14KB**，2025-01-19 后未更新，**无许可证** | 目录结构参考（data/ + templates/），实质内容很薄 |

**建议采纳 B 的"以 bid-toolkit 为形态主轴"，但要加两条限定：**
1. 只能称"形态参考"，不能称"经实践验证的方案"——5 star、1 fork、近一月未更新，不构成验证证据；
2. bid-toolkit 是**直接解析招标文件**的独立工具链（自带 `parse_bid.py`，产出格式要求/废标红线/文件清单/大纲/评分项），**与本套件"必须消费上游解读产物"的接缝规则冲突**。借鉴时必须剥离：只借"产物形状"（JSON 字段划分）与"检查清单"，不借"自行解析招标文件"的路由。

## 5. v0.4 合并方案

### 5.1 结构（A × B 合成）

```
skills-toolkit/
├── SKILL.md                    ← 薄路由（≤80 行）：识别 stage、指路、校验交接、汇总
├── prompts/                    ← B：长提示词独立存放，SKILL.md 只引路径
├── skills/
│   ├── tender-document-review/ ← 已有，不动（v1.1.1）
│   ├── bid-response-plan/      ← ① M1 任务卡 + M3 目录骨架 + 01b/01c 抽取
│   ├── bid-compliance-check/   ← ② M5 废标 + 偏离表 + 形式/一致性（P0）
│   ├── bid-technical-proposal/ ← ③ M4 正文
│   └── bid-docx-export/        ← ④ M6 导出
├── knowledge/                  ← 素材层（B 的写法，补 D8 结构）
├── workdir/                    ← 运行时工作区（gitignore）
└── tests/                      ← fixtures + run_acceptance.py
```

### 5.2 阶段（采 B）

| 阶段 | 内容 | 优先级 | 人日 |
|---|---|---|---|
| 0 | 铁律 7 条、3 个契约 schema、薄路由骨架、反例清单 | P0 | 1–2 |
| 1 | ① 响应策划 + ② 合规自检（含 01b/01c） | P0 | 8–10 |
| 2 | ③ 技术标正文（含 `bid_mode`、素材路由） | P1 | 4–5 |
| 3 | ④ 导出 + 暗标样式档 | P1 | 2 |
| 4 | 端到端 + 四平台矩阵 + `SKILL.lite.md` | P1 | 2–3 |
| 5 | 垂直化（新能源五库） | P2 | — |

### 5.3 必须先补的两个产物

- `01b_spec-items.json`：技术规范条目（偏离表的行来源），由 ① 抽取，只抄行不判定；
- `01c_format-outline.json`：格式章逐字标题与层级（目录骨架的唯一来源），来源标 `user_paste | doc_heading_scan`。

两者共用一条接缝例外：**"仅为条目结构与标题层级可读取原文，不得据此判定评审要点、废标情形或风险等级"**，且产物须留痕 `source_file + page`。
