# 未来升级方向备忘（仓库级开发文档，不属于技能包）

> **归属**：本文件位于仓库 `docs/`，**不属于** `skills/tender-document-review/` 技能包，不随技能一起分发，也不构成运行时依赖。
> **性质**：本文件记录**两条尚未采纳**的架构级建议，供日后真正要做"阶段3 投标文件比对"时启动。
> **重要**：这两条**不属于当前技能的下一步**，**未写入 SKILL.md 主流程**，不构成本技能的依赖或约束。
> 记录目的仅为留存思路，避免反复讨论。

---

## 背景

有专家提出两条"为便于以后升级"的建议。经判定，两条方向正确，但**都不是"投标文件审查"这件事的下一步**——它们是**另一个产品形态**的起点。故记录于此，不进主线。

---

## 方向一：解析层加固——把"靠宿主读 PDF"变成"可控的取数管道"

**专家原建议**：

1. **标准化取数脚本**：固定输出 `P页 \t L行 \t 原文` 格式，行级去重 ＋ 全文子串双口径计数；固化为技能第 1 步取数脚本，而非靠 LLM 临时读。
2. **跨页表格专门处理**：前附表、评分表用 `pdfplumber` 的 `find_tables` 单独抽，不与正文文本混抽（"不要全文直抽、先切块"）。

**判定：采纳为"可选增强"，不进主流程。** 理由：

- 本技能当前定位是**零外部依赖、克隆即用**。加脚本 = 加 `pdfplumber` 依赖 = 开源第一道坎（装上跑不起来）。
- 该建议解决的是**取数稳定性**，不是**取不到/取错**。历轮实测中，缺陷的根因**全部在分类逻辑**，无一项源于取数不稳。
- `P页\tL行\t原文` 双口径计数确为已验证的有效做法，可作为**环境具备该依赖时的可选手段**写入使用说明，主流程仍兼容 LLM 直读。

**若要启动**：在 SKILL.md 第 1 步增列"可选：具备 pdfplumber 时走脚本取数"，并附脚本；**主流程保持 LLM 直读兼容**。

---

## 方向二：结构化中间层——七类清单从"自由文本"变"固定 JSON Schema"

**专家原建议**：

- 先让 LLM 按固定 schema 抽成 JSON（每条带 `类别/事项/原文/出处/金额数值/比例数值/时间节点/澄清修订标记`），再由脚本渲染为 Markdown / Excel 清单。
- 理由：①阶段 3 的投标文件比对，机器要拿"所需响应材料"清单逐一对投标文件，没有结构化 JSON 就做不了；②用户画像中的 Excel 交付、批量处理都建立在这层上；③把口径坑（废标 vs 否决、暗标语境、保证金异名）固化成 schema 枚举字段，不靠"提示词提醒"这种脆弱手段。

**判定：方向认同，但这是"改产品形态"，不是"升级方便"，且与本技能原则存在正面风险。** 理由：

1. **抽取阶段即引入判断**：一旦第一步就是"LLM 按 schema 抽 JSON"，LLM 必须**在抽取阶段就决定"这是一条什么类别"**——这就是判断，而非提取。本技能的原则是"只提取归类、不加工推演"。
2. **服务对象变了**：该 schema 明确"为阶段 3 投标比对服务"——那是**另一个产品**（投标文件响应性比对），不属于"招标文件审查"这一件事。
3. **数值字段诱导越界**：`金额数值` / `比例数值` 字段会诱导"算一算、比一比、判断这个值合不合理"，直接冲撞"只照录不测算"。
4. **枚举固化的收益可低成本获得**：专家说"不靠提示词提醒这种脆弱手段"——但枚举化的**实质内容**（废标=否决、暗标两语境、保证金三名并扫）已经以**规则条目**形式固化进本技能，同样不依赖提示词记忆。

**若要启动**：这是**新建一个技能/产品**的起点，建议独立立项（如 `bid-response-compare`），本技能可作为其上游依赖保持只读，不改主线。

---

## 结论

| 方向 | 处置 | 启动条件 |
|---|---|---|
| 一、解析层加固 | 记录为**可选增强** | 有人明确要求提高取数稳定性，且接受引入依赖 |
| 二、JSON Schema 中间层 | **另立项**，不进本技能 | 真正着手做"阶段 3 投标文件比对"时 |

**本技能当前形态不变**：零外部依赖、只提取不判断、自带交付自检。
