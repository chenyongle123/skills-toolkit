## 3. 完全缺失（12 条，按风险分级）

### L 级：法律风险

**L1. 防串标 / 防雷同（整块空白）**

文档给出的法定核查边界是三个维度：

| 维度 | 触发情形 |
|---|---|
| 方案内容 | 不同投标人技术方案出现**异常一致的段落或特有笔误** |
| 电子属性 | 文档作者、软硬件 MAC 地址、底层机器码完全重合 |
| 需求响应 | 机械套用通用模板，关键参数未实质响应 |

v0.7 现状：全文 0 次"串标/围标/雷同"。§10 只在参考项目表里提到别人有"SimHash 查重""查重四维"，是**借鉴清单**，不是本套件的功能。

后果：本套件生成的是"通用 AI 在相似招标文件 + 相似提示词下输出的结构化文本"，恰好落在最容易撞车的模式里。**没有任何一层做差异化保障。**

**L2. 元数据清理只做了暗标，普通标没做**

v0.7：§8.3 / §11.3 只在 `bid_mode: blind` 时"文档属性作者清空"。
问题：清作者在暗标场景是为**匿名**，防串标要清的是另一组字段——最后修改人、公司名、模板路径、修订记录、打印机名。**普通标项目同样需要**，而 v0.7 对普通标的元数据一字未提。

### M 级：能力缺口

**M1. 技术路线不得由 AI 决定**
需要一条约束：技术路线、实现架构、工艺选择必须来自素材库或用户明示，AI 只做组织与表述。AI 自行设计的路线即使合理也不得进入交付稿。

**M2. M4 缺章节写作五步循环**
提取要求 → 从素材库找可用内容 → **人工确认框架与技术路线** → 按章辅助编写 → 懂行的人逐项核对。
其中第三步是新增人工关卡（暂称 G4），v0.7 没有。

**M3. 逐模块推进节奏**
一次只做一个模块，人工确认后再进下一个。v0.7 的 M4 无此约束，容易退化成"一次生成整本"——正是文档 1 明确批评的做法。

**M4. 交叉验证机制**
文档 1 的实际做法：让 WorkBuddy 和 TRAE **各生成一份文件结构，然后对比，把漏掉的挑出来**。
这比单模型自查可靠——也直接解释了本项目"审核为什么没抓到问题"：同一模型读自己写的东西，盲区是重合的。

## 4. 对 v0.8 的处置建议

1. **新增 §8.6 雷同风险与元数据**：
   - 三维度自查表（方案内容 / 电子属性 / 需求响应）
   - 元数据清理清单（普通标 + 暗标两套字段）
   - 交付前与历史投标文件比对（可选，能做的只有本机历史稿）
2. **铁律 7 条 → 8 条**：新增"技术路线与方案选择须有来源，AI 不得自行设计"。
3. **M4 补五步循环 + G4 关卡**（技术路线人工确认，位置在 ③ 写正文前）。
4. **② 增加"雷同自查"检查类**（D 类）：检出通用套话密度、结构模板化程度、与历史稿的相似段落。
5. **新技能或将 ④ 扩展**：`verify_docx.py` 增加元数据检查 + 中英文空格检查。
6. **`写作规范.md` 必须有实体内容**，不能只留文件名。

## 5. 一条方法论启示（直接回应当前问题）

文档 1 的做法值得抄进本项目的**工作流**，不只是抄进技能：

> 让两个不同的模型各出一版，然后对比，把漏掉的挑出来。

本项目的 29 处问题，绝大多数是"同一模型读自己写的东西"漏掉的。**交叉验证比自查有效**，因为盲区不重合。

建议：v0.8 定稿前，把计划投给另一个模型独立审一遍（不给它看已有意见），再与我这三轮的清单合并去重。
